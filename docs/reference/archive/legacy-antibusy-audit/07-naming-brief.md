# Naming brief

## Verified product essence

The current product is a **desktop workspace for directing a tool-using coding agent inside project-backed conversations**. It combines visible human control with agent execution: the user chooses a project, session, mode and model, submits work, watches streaming replies and tool activity, answers questions, reviews plans, and can stop or cancel work.

## Primary user job

> Work with an AI coding agent on a local project while retaining visibility and decision points over its plan, tools, context and execution.

## Verified product signals

| Signal | What the user can do now |
| --- | --- |
| Workspace-aware | Select/relink project directories and open project-associated sessions. |
| Conversational | Start, restore, switch and review long-lived conversations. |
| Tool-using | Watch file/shell/search/web-like tool calls and their outputs in the chat. |
| Controlled execution | Stop an agent, approve/reject plans, answer its questions and respond to confirmations. |
| Configurable intelligence | Choose mode/model/reasoning and persist advanced context/tool behavior. |
| Context-efficient | Agent behavior can use compressed tool context and virtual file representations. |
| Observable | Inspect stream state, tasks, usage, logs, sub-agents and MCP status. |
| Extensible by configuration | Advanced mechanisms exist for custom tools, hooks, skills, MCP and sub-agent policies, mostly startup-oriented. |

## Positioning, based on evidence

- Not only a chat client. The defining unit is a **project-associated agent session**.
- Not an unattended autonomous system. Plan approval, questions, confirmations, Stop and cancellation make **guided control** central.
- Not an IDE replacement by current evidence. There is no proved active general Files panel or editing workspace.
- Not an MCP manager. MCP status is surfaced, but server administration is not.
- Not primarily a multi-agent console. Sub-agents are model-initiated support workers, surfaced for observation and cancellation.

## Naming criteria

A future name should suggest:

1. An agent that works within a user's project/workspace.
2. Cooperative direction and visibility, rather than opaque autonomy.
3. Practical engineering activity, not generic conversation.
4. Memory, context or continuity, only if this remains a v1 product promise.
5. A short, pronounceable identity that can survive removal or redesign of current implementation details.

Avoid names that imply:

- guaranteed fully autonomous delivery;
- a full IDE or source editor;
- direct ownership of all model/provider infrastructure;
- only terminal/CLI usage, since the audited product is desktop-first;
- a narrow single-model or single-protocol identity.

## Candidate semantic territories, not names

- **Guided maker:** direction, cooperation, deliberate execution.
- **Project companion:** continuity, local workspace, engineering support.
- **Visible operator:** tools, plans, review, action transparency.
- **Context navigator:** large-codebase orientation, retrieval, focused work.

Do not choose a final name before deciding which advanced behaviors, especially context compression, VFR, extensibility and plan/permission control, are required in the rewrite's first release.
