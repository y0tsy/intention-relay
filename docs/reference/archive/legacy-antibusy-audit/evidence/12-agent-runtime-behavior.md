# Agent runtime behavior: UI-reachable static evidence

**Scope and method.** This is a static-code audit at repository commit `8604fde`. A behavior is included only where the desktop frontend exposes a session or configuration route that reaches the corresponding agent machinery. “Impact” below describes the code-defined output/state the user can observe; it is not a claim that a specific run occurred. The config editor exposes the complete generated `Config` schema and raw TOML, reads it through `configService`, and saves via `updateConfig`/`updateConfigFromToml` (`crates/tauri-app/frontend/src/components/ConfigEditor.svelte:41-52,102-116`). Both backend commands parse, validate, persist, and replace `AppState.config` (`crates/tauri-app/src/commands.rs:1195-1238,1251-1293`). The chat input routes to `send_message` (`crates/tauri-app/frontend/src/App.svelte:82,161-165`; `crates/tauri-app/frontend/src/lib/chat-service.ts:22-69`), which obtains/creates an `AgentLoop` and runs it (`crates/tauri-app/src/commands.rs:411-468`).

## Included behavior chains

### 1. Headroom/CCR compression and recovery

**UI-mediated path.** The UI can save `[context.headroom]` via the generic configuration editor. At app-state construction, `AppState::new` copies `config.context.headroom`, builds a `HeadroomPipelineAdapter`, registers `retrieve` only when that pipeline exists, and attaches the pipeline to each newly created agent (`crates/tauri-app/src/state.rs:78-83,166-169,388-423`). Thus the static path for a newly created/restored agent is:

`Config editor → update_config(_from_toml) → AppState.config → create_agent → AgentLoop::with_compression → ToolRunner::compress_tool_result`.

**Agent effect and visible consequence.** `ToolRunner` executes each successful tool call through compression before storing the tool message, except `retrieve` and `llm_call`; it sends the result to the frontend *before* its session-message truncation step (`crates/core/src/agent_loop/tool_runner.rs:270-330,194-229`). Therefore the tool-result content streamed to the chat and supplied back to the model may be the compressed form. The adapter skips empty/small text and source code, runs the Headroom pipeline for eligible content, emits antibusy `<<ccr:HASH>>` markers when an offload key exists, and can retain/recover original content (`crates/compression/src/adapter.rs:79-207`). The `retrieve` tool can list tracked hashes or return originals by one/multiple hashes; missing/expired values return an error (`crates/tools/src/retrieve.rs:34-118`).

**Demonstrated defaults/limits.** Headroom is enabled by default; default CCR backend is in-memory, capacity is `1000`, TTL is `1800` seconds, minimum compression input is `500` characters, ML detection is off, and all five listed pipeline toggles are on (`crates/config/src/types.rs:489-530`; `crates/config/src/constants.rs:18-28`). The pipeline honors `enabled = false`; it selects SQLite CCR only when configured (with in-memory fallback if creation fails), and independently applies the configured transform switches (`crates/compression/src/pipeline.rs:25-105`). The adapter caps only its tracked-key *set* at `100,000`, clearing that tracking set if exceeded; this is not a demonstrated CCR-store capacity (`crates/compression/src/adapter.rs:15-17,154-164`).

**Startup/reload caveat.** The config-save commands replace only `state.config`; they do not rebuild active agents or the `AppState.compression` pipeline (`crates/tauri-app/src/commands.rs:1223-1238,1281-1293`). The construction/attachment chain above is demonstrated for an `AppState` initialized from the configuration, not as a live effect of Save in the currently running process.

### 2. VFR: virtual source-file reads and model instructions

**UI-mediated path.** The same configuration editor exposes `[context.vfr]`. `AppState::new` builds `VfrBuilder` with that configuration and registers VFR-backed `read`, `edit`, and `expand` tools (`crates/tauri-app/src/state.rs:81-83,119-169`). `create_agent` also assembles and appends the system prompt before the chat path calls `AgentLoop::run` (`crates/tauri-app/src/state.rs:424-485`; `crates/tauri-app/src/commands.rs:411-468`).

**Agent effect and visible consequence.** The `read` tool uses VFR when the builder says the path and line count qualify; for non-`raw` reads it returns the virtual representation, while `raw: true` retains the complete content and still registers its map (`crates/tools/src/read.rs:107-145`). The builder returns passthrough unless VFR is enabled, the file has at least `min_lines`, and its detected language is in the configured list; otherwise it parses/builds a source map and hides configured regions (`crates/vfr/src/builder.rs:25-83`). Consequently, the tool result visible in the chat/model context can contain virtual placeholders rather than source bodies.

`build_system_prompt` always adds `VfrInstructionsSource` using `config.context.vfr.enabled` (`crates/tauri-app/src/state.rs:516-575`). When enabled, that source tells the model that reads of large files return placeholders and directs it to `expand` or `raw: true`; when disabled it contributes no text (`crates/prompt/src/sources/vfr_instructions.rs:19-58`). This makes the representation and the instructions part of the same UI-configured agent behavior.

**Demonstrated defaults/limits.** Defaults are enabled; `min_lines = 200`, `min_body_lines = 5`; languages are Rust, Python, TypeScript, JavaScript, and Go; import/test collapse and doc-comment preservation are enabled (`crates/config/src/constants.rs:36-62`; `crates/config/src/types.rs:532-555`). The prompt text itself says “>200 lines” (`crates/prompt/src/sources/vfr_instructions.rs:19-26`), but the executable threshold is the configurable `line_count < min_lines` check (`crates/vfr/src/builder.rs:69-82`); the code check is authoritative for this audit.

### 3. Prompt sources, including project instruction and memory files

**UI-mediated path.** The config editor exposes the `[prompt]` fields. A session is created from the UI (`crates/tauri-app/frontend/src/App.svelte:100,175`; `crates/tauri-app/src/commands.rs:31-104`), which calls `create_agent`; that function calls `build_system_prompt`, stores the result as a system prompt in the session, then the user can send chat input through `send_message` (`crates/tauri-app/src/state.rs:424-485`; `crates/tauri-app/src/commands.rs:411-468`).

**Agent effect and visible consequence.** `build_system_prompt` resolves configured `agents_file` and `memory_file` against the session’s selected project directory when one exists. It unconditionally adds identity, guidelines, tool usage, memory instruction, session path, date, mode, git context, and coding conventions; it conditionally reads the resolved `AGENTS.md` and memory files only if their auto-load flag is true and the file exists; it conditionally adds few-shot examples and MCP prompts (`crates/tauri-app/src/state.rs:516-575`). The resulting source text is sorted by descending priority, joined, and capped at 100,000 characters with a truncation notice (`crates/prompt/src/builder.rs:7-85`). The visible effect is indirect but user-relevant: the model’s tool choices and replies are conditioned by those session system messages.

**Demonstrated defaults.** Defaults are `agents_file = "AGENTS.md"`, `memory_file = ".antibusy/memory.md"`, `auto_load_agents = true`, `auto_load_memory = true`, and `few_shot_examples = true` (`crates/config/src/types.rs:466-476`). The documented fixed prompt-builder cap is 100,000 characters (`crates/prompt/src/builder.rs:7-8`).

### 4. Custom shell tools

**UI-mediated path.** The configuration schema includes `custom_tools` (`crates/config/src/types.rs:15-40`), so the config editor can persist definitions. At next application initialization, `AppState::new` constructs `CustomToolRegistry` from `config.custom_tools` and registers every custom tool into the main tool registry (`crates/tauri-app/src/state.rs:171-177`). A UI chat turn then gives the model the registered schemas through the agent’s executor (`crates/core/src/agent_loop/run.rs:115-148`).

**Agent effect and visible consequence.** A custom tool’s configured description and JSON schema are exposed as its LLM tool definition; invoking it substitutes named `{argument}` placeholders, shell-quotes substituted values, runs the configured shell command in an optional working directory, and returns stdout on zero exit. It returns an error with stdout/stderr on nonzero exit (`crates/core/src/custom_tools/mod.rs:65-125`). Tool start/result events are streamed to the frontend as the agent runs (`crates/core/src/agent_loop/tool_runner.rs:95-180,331-365`), so the tool name, arguments, and returned result/error are user-visible in the chat UI.

**Startup/reload caveat.** The config-save commands replace only `state.config`; they do not rebuild the base tool registry (`crates/tauri-app/src/commands.rs:1223-1238,1281-1293`). The demonstrated registration point is `AppState::new`, so static evidence supports an `AppState` initialized from the definition, not live installation after Save.

### 5. Configured lifecycle/tool hooks

**UI-mediated path.** The config schema exposes hook entries (`crates/config/src/types.rs:15-40,121-160`). At application construction, config hook entries become a `HookManager` and every subsequently created agent receives it (`crates/tauri-app/src/state.rs:238-241,401-423,499-510`). A UI chat message reaches `AgentLoop::run`, which fires `SessionStart` and `SessionEnd`; tool calls reach `ToolRunner`, which fires `PreToolUse` and `PostToolUse` (`crates/core/src/agent_loop/run.rs:29-70,450-468`; `crates/core/src/agent_loop/tool_runner.rs:117-160,194-229`).

**Agent effect and visible consequence.** Each registered hook is executed sequentially as `sh -c` with its event/session/tool argument/result values provided through `ANTIBUSY_*` environment variables. Hook failures are collected but do not prevent remaining hooks; the agent call sites log warnings and continue (`crates/hooks/src/executor.rs:30-124`; `crates/core/src/agent_loop/run.rs:450-468`; `crates/core/src/agent_loop/tool_runner.rs:134-160,204-229`). The direct user-visible impact is any filesystem/process effect or tool/session outcome caused by the configured command, plus the normal tool result stream; the code does not route hook stdout/stderr to the chat as a distinct UI message.

**Startup/reload caveat.** The config-save commands replace only `state.config`; they do not reload the hook manager (`crates/tauri-app/src/commands.rs:1223-1238,1281-1293`). The static construction path applies to an `AppState` initialized with the configured hooks, rather than a hook added by Save to the presently active process.

### 6. Skills and skill-based tool filtering

**UI-mediated path.** `active_skills` is a top-level config field in the UI schema (`crates/config/src/types.rs:15-40`). Startup loads `.antibusy/skills/*.toml`, activates only names in `config.active_skills`, and stores the registry (`crates/tauri-app/src/state.rs:179-191`). `create_agent` derives a tool filter from that registry, wraps the mode/CWD/MCP chain, and appends active skills’ prompt additions as a system message (`crates/tauri-app/src/state.rs:342-385,469-485`). A user chat turn then builds an LLM request from that filtered executor’s schemas (`crates/core/src/agent_loop/run.rs:115-148`).

**Agent effect and visible consequence.** Active skill prompt additions are concatenated beneath `# Active Skills` (`crates/skills/src/lib.rs:185-212`). If skills set `allowed_tools`, their sets are intersected; blocked tools are removed and take precedence. With only blocks, the filter denies those names; with no restrictions, all tools remain available (`crates/skills/src/lib.rs:214-250`). `SkillFilteredExecutor` removes unavailable schemas, reports unavailable tools as absent, and refuses direct execution with “Tool not allowed by active skill” (`crates/core/src/mode/skill_filter.rs:15-75`). Thus the model sees a restricted tool set and the UI receives only calls/results of allowed tools.

**Activation caveat.** There is no frontend skill-toggle command. The UI-reachable route is configuration plus application initialization; saving config itself does not reload the registry or rebuild the current loop (`crates/tauri-app/src/commands.rs:1223-1238,1281-1293`). Only skills that exist under the fixed `.antibusy/skills` directory at initialization and whose names appear in `active_skills` are statically demonstrated as active.

### 7. Sub-agents: agent-initiated spawning plus UI status/cancellation

**UI-mediated path.** The main registry registers `spawn_sub_agent` (`crates/tauri-app/src/state.rs:130-169,224-230`), so a UI-submitted chat turn can lead the model to invoke it. The spawn tool builds an isolated request from the model’s prompt/type/mode/model/max-iterations fields, gives it the fixed sub-agent registry, and passes it to the orchestrator (`crates/tools/src/spawn_sub_agent.rs:30-111`). Separately, the frontend `SubAgentsPanel` fetches `getSubAgents` and exposes a Cancel button (`crates/tauri-app/frontend/src/components/SubAgentsPanel.svelte:15-26,66-90`); App wires cancellation to `cancelSubAgent` (`crates/tauri-app/frontend/src/App.svelte:167-177`), whose backend cancels the orchestrator job (`crates/tauri-app/src/commands.rs:1501-1534`).

**Agent effect and visible consequence.** The parent model can cause a foreground child result or receive an immediate background child ID, per the tool’s mode mapping (`crates/tools/src/spawn_sub_agent.rs:48-55,91-111`). The UI receives forwarded lifecycle events from the orchestrator and renders running type, elapsed time, depth, mode, and cancellation control (`crates/tauri-app/src/lib.rs:139-184`; `crates/tauri-app/frontend/src/components/SubAgentsPanel.svelte:66-90`).

**Demonstrated defaults/limits.** Global orchestration defaults are max concurrent `10`, timeout `300` seconds, and nesting depth `5` (`crates/config/src/constants.rs:10-16`; `crates/config/src/types.rs:514-530`). Per-type entries can specify allow/deny lists and a model override in the config schema (`crates/config/src/types.rs:519-530`), and `AppState::new` installs them into the orchestrator (`crates/tauri-app/src/state.rs:207-222`). The `spawn_sub_agent` *tool* uses its separate prebuilt base registry (read/write/edit/execute/glob/grep/fetch_url/expand), not the parent’s dynamically filtered/MCP/custom registry (`crates/tauri-app/src/state.rs:108-159`; `crates/tools/src/spawn_sub_agent.rs:24-29,96-105`). This distinction is static evidence of child isolation.

### 8. General user-controlled loop/output limits that shape all UI chat turns

This is included because the configuration editor exposes `agent_loop` and `context.max_tool_result_chars`, and `create_agent` copies them into the loop for UI-created/restored sessions (`crates/config/src/types.rs:15-40,285-307`; `crates/tauri-app/src/state.rs:278-337`). The request carries `max_output_tokens`, and the loop stops with a text result when configured `max_iterations` is reached (`crates/core/src/agent_loop/run.rs:115-148,230-270`). Tool results are streamed first, then session history gets a character-boundary-truncated copy suffixed with `[truncated]` if it exceeds `max_tool_result_chars` (`crates/core/src/agent_loop/tool_runner.rs:194-229`).

Defaults: LLM timeout 120 seconds, parallel tool calls true, `max_output_tokens = 4096`, `max_iterations = 1000`; rate-limit retries 5, server-error retries 3, backoff 1000–30000 ms with jitter (`crates/config/src/agent_loop_config.rs:9-74`; `crates/config/src/constants.rs:1-8`). `max_tool_result_chars` defaults to `50,000` (`crates/config/src/types.rs:480-487`; `crates/config/src/constants.rs:30-31`). The global configuration is copied while creating an agent, rather than immediately mutating an active `AgentLoop`; the current `AppState` also retains its startup-created base tool registry/compression pipeline.

## Deliberately excluded as not shown UI-reachable

* The public `spawn_sub_agent` Tauri command is registered (`crates/tauri-app/src/lib.rs:31-81`) but the inspected UI exposes status/cancellation, not a direct manual “spawn sub-agent” control. The report includes only model-mediated spawning from a chat turn, not a user-facing manual spawn workflow.
* MCP auto-connect, server tool filtering, and MCP prompt injection are config-backed backend mechanisms, but the inspected UI exposes only `getMcpStatus`; no UI command creates/edits/connects server definitions. They are excluded under the requested UI-path rule (`crates/tauri-app/frontend/src/lib/application-service.ts:41-44`; `crates/tauri-app/src/lib.rs:185-250`).
* VFR LSP fields are present in config but no static path from these fields to an instantiated LSP client or write validation was found in the required chains; they are excluded.
* CCR key-list tracking internals, compression content-detection implementation, model cache-hit warnings, conversation normalization/unknown-tool repair, and raw provider retry mechanics are backend-only within the UI chat flow. They are not presented as separately configurable/UI-mediated mechanisms in this report.
